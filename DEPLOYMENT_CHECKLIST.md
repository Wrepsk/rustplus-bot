# Live deployment checklist

## Camera viewer — requires a real Rust server

- [ ] Rebuild with the existing Compose web override. Confirm `/camera`, its assets and `/camera/api/` pass through the current HTTPS reverse proxy. No new DNS or public port is needed.
- [ ] Register a powered camera identifier (not an entity ID), choose the correct server and view the feed while your paired player is offline and alive. Verify actual orientation and the ray-only rendering limitation (no separate entity/player-name overlays).
- [ ] Run `/camera panel` for two servers in one Discord channel. Confirm each dropdown opens a private link for the correct server, without editing the public panel. Refresh, rename, pause/resume, add/remove a camera, restart the bot and move one panel; only its current message may work. Existing switch panels must remain unchanged.
- [ ] Compare stationary, slow pan and drone translation against the official Rust+ app, sequentially using the same camera/account. Record packet/render/display FPS and confirm **Stable ray reconstruction** is shown. Check for reversed movement, shaking, layout jumps, speckles, ghosts and newly revealed holes; synthetic ray tests do not prove live rendering quality.
- [ ] Test PTZ look controls, then drone movement in an empty, safe area. Verify every pulse releases, directions are correct and latency is usable. Test turret aim only; firing/reload must be absent. Unsupported movement must be rejected server-side.
- [ ] While online, confirm another account cannot be borrowed until its owner enables sharing on that server. Revoke sharing and verify closure; repeat with unlinking, role revocation, owner login/death, server pause/restart and network loss. No automatic account switch after failure.
- [ ] Open simultaneous viewer links for one server; only one should succeed. Exercise different servers in visible browser windows, expired/reused links, hidden tabs, abandoned viewers, stale frames and bot restart. Confirm chat and alarms keep working.
- [ ] Verify unauthorized users cannot register cameras, use another member's menu or send controls. Confirm Rust tokens and session cookies never appear in Discord, pages or proxy/application logs.

Camera automation tests use mocks, a local synthetic Rust+ WebSocket and generated rays. They do **not** verify a live camera or physical drone response.

Automated mocks and the local protocol test cover application behavior. Every unchecked item below requires your Discord guild, Rust server, VPS or Docker Engine; none was verified with real credentials during this review. Use harmless test circuits first.

- [ ] Back up the entire stopped data volume before updating, including `credentials.key`, every `servers/` database and WAL/SHM files. Keep `.env` and desktop pairing files private; run one bot instance per data volume.
- [ ] Run `docker compose config --no-env-resolution --quiet`, `docker compose build --pull`, then `docker compose up -d` on the x86-64 Ubuntu VPS. Confirm the non-root process can create/write `/app/data/bot.sqlite` and logs contain no secrets.
- [ ] Verify Discord authentication, guild slash commands, Message Content Intent and panel/chat/alert channel permissions. Configure the existing alert channel with `/settings alerts`; run `/alarm test` and verify its simulated label and intended role ping.
- [ ] Complete desktop `fcm-register` / `fcm-listen` and in-game server pairing. Use the notification's app port, Steam64 ID and player token. `/status` must show connected, a last-success time and operational monitoring.
- [ ] Pair a real Smart Switch in-game, register its entity ID/type/name, then create `/panel`. Confirm the initial ON/OFF matches the switch in-game.
- [ ] Test ON, OFF, Refresh and rapid repeated clicks. Verify actual switch state, no false success on failed reads, and independent operation of a second switch. Door position must not be inferred from switch power.
- [ ] Register a harmless switch as sensitive; confirm it cannot change without the user-bound confirmation. Test another user's confirmation attempt and an expired confirmation.
- [ ] Test an ordinary member without an allowed role: buttons, direct/stale components and Discord-to-Rust relay must not operate. Remove an operator role and verify access is revoked; administrative commands stay restricted.
- [ ] Pair/register a powered Smart Alarm wired to a sensor. Establish an inactive baseline, activate it and verify exactly one normal raid alert. Verify continued activity and rapid toggling respect deduplication/cooldown. Disable it and verify silence.
- [ ] Leave an enabled alarm active across a reconnect/restart: expect the distinct **Alarm Active After Reconnection** warning, no fabricated raid alert and no recovery-warning role ping. Reconnect again while active: no duplicate warning. Observe inactive, then test normal activation and a later monitoring-gap warning.
- [ ] Configure `/chat setup`. Verify original Rust player names/text in Discord and `[Discord] DisplayName:` in Rust, both without echoes. Check mentions, Unicode, long text, bots/webhooks, attachments-only messages and changing team membership.
- [ ] If using website pairing: configure the actual `PAIRING_WEB_URL`, Compose web override and existing HTTPS reverse proxy. Confirm HTTPS/root/static assets, no publicly exposed 3080, and private session codes absent from access logs. Download the generated extension ZIP, extract, Load unpacked in desktop Chrome/Edge, then refresh the pairing website. Confirm Extension connected. Follow `/pair start` → website sign-in button → official Facepunch warning (approve manually) → Steam login → original website tab → Create Discord command → encrypted import in Discord. Verify no desktop app is required and no raw token appears in URLs/logs/storage generated by the extension. This Steam/FCM/Chrome integration requires a real-account smoke test; unit tests use mocks.
- [ ] Exercise inbox Accept/Decline, naming and sensitive-switch dialogs, pagination, duplicate submissions and stale entries. Confirm personal server linking never replaces the shared monitoring identity. Test another user's buttons and revoked roles. Use device/alarm dropdowns, rename/removal confirmation, simulated alert, chat toggle and server selector; verify original switch panels still work after restart.
- [ ] Disable the extension and verify the website blocks sign-in with installation instructions. Reload/re-enable it, refresh the website and retry with a fresh challenge. Test an old login tab, refresh during sign-in, expired code, simultaneous users, duplicate native/redirect messages, wrong origin/nonce, failed registration, cancellation and bot restart. An official app-page redirect must never be accepted as successful pairing. Extension installation, MAIN/isolated-world timing and the real consent page need browser testing beyond mocked callbacks.
- [ ] Update unpacked extension files and Reload its card after deploying extension 1.0.2; the VPS update cannot update an installed extension. Confirm the website rejects 1.0.0/1.0.1. Click Continue on Facepunch yourself and verify the original website receives the result before the login tab closes. On a failed handoff, verify a fixed diagnostic code, no false success, and no credentials in console output. Synthetic automated tests cover Base64 `+`, `/` and `=` preservation; live registration remains a separate check.
- [ ] Owner: build/publish the Windows helper ZIP and set its actual HTTPS `PAIRING_HELPER_URL`. Verify `/pair start` has a working download button and gives a code, without repository/npm instructions. A friend on Windows with Chrome but **without Node.js or this repository** must be able to extract the ZIP, double-click `RustPlus Pairing.cmd`, link through Steam and copy the encrypted import command. Check cancellation, retry, code expiry, Sign in again, and Reset local registration. Real browser/Steam login requires a live check; automated packaging smoke tests use synthetic saved credentials only.
- [ ] Import the helper's encrypted command, verify `/pair status` shows listening, then close the helper/local fcm-listen. Pair a server and a device in-game; accept each through the private `/pair inbox`. No token should appear in Discord or bot logs. Restart the container and verify pairing notifications still arrive without a desktop listener.
- [ ] Link a second authorized Discord user to the same server, with their own Steam/Rust+ pairing. Verify their outgoing chat uses their actual Steam identity, has the existing Discord prefix, and is not echoed. Unlinked authors must get a clear failure and must never use the owner's identity. A paired player in another Rust team must be rejected. Revoke a personal token and verify retries pause until a fresh pairing is accepted.
- [ ] Add a second server with separate chat/panel/alert channels. Verify both servers monitor simultaneously and overlapping entity IDs cannot cross-control. Exercise explicit `server:` selection, channel routing, `/server use`, pause/resume, and recovery independently. Restart/recreate and verify each server's registrations, history and channels persist.
- [ ] Run `/panel` twice in one Discord channel, selecting different servers. Verify both panels show their server names and buttons control only that server even with overlapping entity IDs. Refresh and restart; both panels must remain independent. Move a panel from another channel by running `/panel` in the shared channel: the previous message must have inactive controls. A failed new-panel send must leave the old panel functional.
- [ ] Run `/server rename name:Trio Vanilla`, choose a server and verify its picker/list/panel labels and future alerts update without a Rust reconnect. Confirm devices, channels and personal links remain intact, and the name survives recreation. Test a paused server, rejected blank/overlong names and a non-administrator attempt.
- [ ] With two saved servers, run `/settings alerts channel:#alerts` and `/chat setup channel:#rust-chat` without IDs. Check the private dropdown preserves options and runs only after choosing the intended server, including from another server's channel. Test Cancel, expiry, duplicate clicks, role revocation, another user's forged selection and old menus after restart. `/server use`, pause and resume must work without IDs; existing panel buttons remain bound to their original server. Explicit `server` IDs still skip the picker.
- [ ] Give two servers the same `/settings alerts channel:#alerts` destination by selecting each server in turn. Test alerts from both and verify each footer names its own server. Player activity notices must not ping the raid role or mentions embedded in player names.
- [ ] With a known teammate initially offline, wait for synchronization, then have them log in and out. Expect one corresponding player notice per transition (broadcast or within roughly 30 seconds). Reconnect/restart while they remain online: no fabricated notice. Check with chat disabled as well.
- [ ] Link your personal Rust+ registration, accept the relevant server and verify `/pair status` is listening. Log out of Rust and have your sleeping player die in a controlled test. Expect one clearly labeled Rust+ death push in that server's alerts. Test a second linked player, duplicate delivery/restart deduplication, and queued Discord delivery during a gateway interruption. This needs real Rust/FCM; mocked tests cannot guarantee upstream push delivery.
- [ ] Run `/chat setup channel:#occupied-chat server:<new-server-id>` as an administrator. Verify the new server owns it, the old bridge is disabled with no channel, old queued sends fail safely, and no cross-server echo appears. `/chat enable` on the old server must require setup first. A non-administrator must be unable to transfer it. Check persistence after recreation.
- [ ] Run `/pair unlink` as a friend and as the owner: personal credentials/listener must stop, queued sends must fail safely, and shared monitoring must continue. Unlinking must survive a restart. Check personal connections close after idle time and peak connections fit your server's configured per-IP limit.
- [ ] Interrupt Rust connectivity briefly (<60s): no connection notice. Interrupt it for >60s: one loss notice; controls become unavailable and Discord chat sends receive failure feedback. Restore it: one recovery notice with downtime after subscriptions initialize; panel refreshes and chat resumes without replaying history.
- [ ] Make one registered device inaccessible: `/status` and any outage recovery must show degraded monitoring. Repair/pair it and confirm a subsequent maintenance cycle restores its state.
- [ ] Restart the Rust server and test switches, alarms and both chat directions afterwards. Test temporary proxy/internet loss. If credentials are revoked, verify `invalid-credentials`, paused retries, and recovery after re-pairing/update/recreation.
- [ ] Interrupt Discord connectivity: confirm its gateway reconnects, pending alert/connection notices eventually deliver in the correct order and no new event-listener duplicates appear.
- [ ] `docker compose restart`, then `docker compose up -d --force-recreate`: registrations, roles, cooldowns, outboxes and panel message persist. No historical chat or ordinary baseline raid alerts appear.
- [ ] Reboot the VPS with Docker enabled at boot; verify `unless-stopped` recovery. Confirm an intentional `docker compose stop` remains stopped. Never use `down -v` to test persistence.

- [ ] Camera streaming/keyboard smoke test: open a fresh `/camera watch` link after rebuilding. Record ray packets/s, render/display FPS and frame age for CCTV, PTZ and a drone. Verify frames arrive continuously through Nginx without ten-second batches. Test WASD/diagonals, arrow look, Space ascent, Shift descent, key release, Escape, window blur, hidden tab and network loss. Check the physical drone stops receiving held movement on release/timeout; acknowledgements alone are not proof. Confirm slow/failed input closes the viewer without replay, and alarms/chat remain responsive during viewing. Synthetic tests cannot establish real FPS or physical control behavior.

- [ ] Camera reconstruction: verify W/Up looks up and S/Down looks down on PTZ/turrets. Compare stationary clarity before/after a sample sweep, then pan or fly: received detail should remain at native resolution, with gap filling limited to missing pixels. Check thin edges and foreground/background separation for blur, and confirm that shaking and unsampled black speckles have not returned. Stop and verify stationary coverage rebuilds. Check low packet rates, genuine dark surfaces, abrupt direction changes and sustained motion. Automated decoder tests use a public captured fixture and cannot establish the quality of this server's live stream.

Notifications use an at-least-once persistent outbox. A crash after Discord accepts a message but before SQLite acknowledges it can duplicate that message. Alarm changes wholly within an offline interval cannot be reconstructed; an active recovery warning only reports the observed baseline.
