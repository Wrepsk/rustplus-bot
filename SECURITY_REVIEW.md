# Dependency and application security review

Reviewed 2026-10-11 against the installed lockfile and upstream source. Both `npm audit --json` and `npm audit --omit=dev --json` report **11 moderate, 0 high, 0 critical** affected package entries. These are four underlying advisories plus inherited dependency-chain findings, not eleven independent exploits. All are included in the production installation because rustplus.js bundles pairing/camera dependencies; none is development-only.

`npm audit fix --dry-run --json` proposed **0 changed / 0 removed packages** and retained all 11 findings (optional packages for other platforms were listed as additions). No safe compatible fix was available from that operation. No dependency versions, lockfile or Rust+ protocol library were changed. Existing protobufjs, form-data and qs security overrides remain.

## Application findings

The browser-pairing addition reran `npm audit --omit=dev --json`: **11 moderate, 0 high, 0 critical**, unchanged. No dependencies were added. Website registration is now production-reachable when explicitly enabled; the request-chain assessment above reflects that change. Steam/Facepunch sign-in remains in the user's normal browser. The user manually pastes the nonce-bound loopback result into the HTTPS pairing page; only a Rust+ companion token is temporarily sent to the VPS, not Steam passwords, Guard codes or cookies. This is not a Steam OpenID substitute or a claim of live integration testing.

- Website pairing is disabled by default. The optional Compose override exposes only host loopback to an existing HTTPS reverse proxy. Active Discord challenges gate registration; secure HttpOnly SameSite cookies, exact Origin checks, CSRF tokens and exact loopback/nonce parsing protect completion. Pasted URLs are never fetched. Secret payloads use POST bodies; Discord codes use URL fragments and are removed from browser history on load. No analytics, external scripts, raw upstream errors or body logging are added.
- Browser sessions are bounded to 50, expire within 15 minutes and are periodically pruned. Registration has a two-worker cap, global 30-attempt/hour bound, per-session failure limit and 60-second worker deadline. Repeated completion returns the same encrypted result rather than repeating registration. Shutdown aborts workers. Worker stdout/stderr are drained privately to suppress upstream token-bearing logs. Google app identifiers in registration-worker.ts are public companion app constants, not user credentials.
- Inbox, server and management components are bound to the clicking Discord user and configured guild. Permissions are fetched afresh for modal submissions and mutations. A name dialog never activates a device. Reaccepting cannot clear a switch's existing sensitivity flag. Existing switch control confirmations, IDs and saved message routing remain intact. New remove/unlink controls ask for confirmation; decline only clears a pending inbox entry.

The multi-server extension reran `npm audit --json`: 11 moderate, 0 high, 0 critical, unchanged. No dependencies or overrides were added. The push receiver is now loaded in the VPS runtime, so the legacy pairing-only reachability assessment has been updated above. Its inherited check-in/retry helper is overridden with native fetch against Google's fixed HTTPS endpoint, a 15-second abort timeout, and no raw error logging. Socket/parser errors are caught; push buffers and deduplication IDs are bounded; FCM login failures stop retries until reimport. Unsupported encrypted-webpush notifications are ignored; supported plain pairing notifications are validated before saving. This does not fix the vulnerable dependencies themselves or establish live compatibility with every FCM service change.

- Local registration remains the upstream Chrome/Steam flow on the user's PC. The helper captures/discards upstream token-bearing console output and transfers only the FCM Android ID/security token, not Steam credentials or companion auth tokens.
- The Windows portable helper includes a checksum-verified official Node runtime and locked production dependencies; explicit packaging allowlists exclude the working tree's secrets and all real registrations. Its UI launches the helper using fixed executable paths and validated public codes without a command shell, never shows arbitrary child output, and bounds sign-in to 12 minutes. Closing it terminates its own registration process tree. Successful desktop registration drops unused companion/Expo credentials from the local file. The CLI fallback retains its file unless explicitly asked to minimize it.
- The packaged upstream CLI has two checked compatibility edits: bind its temporary login callback to `127.0.0.1` and remove the hardcoded Unix Chrome profile flag so chrome-launcher creates/cleans an isolated temporary profile. The upstream cross-origin Chrome login mechanism is retained, including its browser-security flags; use that dedicated window only for pairing. The same inherited pairing dependency advisories remain; packaging them does not remediate those libraries. No Steam sign-in or FCM registration was exercised with live credentials.
- Pairing imports use ephemeral X25519 key exchange, HKDF-SHA256 and AES-256-GCM. Challenges are Discord-user-bound, expire after 15 minutes, and are consumed once. Inbox payloads and imported server/player/FCM credentials are AES-GCM encrypted at rest with context binding. The random 32-byte key is created with mode 0600 beside the data files. Missing keys on an existing installation fail startup rather than silently replacing them. Back up the whole data volume privately.
- Users can only accept their own inbox entries. New monitored servers and all device registrations require administrator access. Personal pairings must match an existing approved endpoint, and chat checks membership in the monitoring team. Personal credentials cannot replace a different monitoring Steam identity. Explicit unlink is permitted after role revocation and survives restart.
- A single Discord dispatcher routes persistent panel messages to their original server and isolates per-server databases/settings. Explicit server selection and role checks are enforced on the server; no component ID selects an unregistered entity or an arbitrary server/Steam identity.
- Personal chat requires linking with no shared-account fallback, retains the Discord author prefix, suppresses echoes from linked/previous sender identities, bounds additional sockets and closes idle connections. Uncertain sends are not retried. The owner is initially linked only from their preexisting environment pairing.

- Server-side member fetches and role checks protect every switch/confirmation interaction; forged component IDs cannot select unregistered entities or bypass sensitive confirmations. Confirmations are user-bound, single-use and expire after 30 seconds.
- Operator `@everyone` is rejected in initial environment configuration and role-add settings. Authorization also ignores any legacy persisted `@everyone` entry; administrators can remove that entry with role-remove. Ordinary server administrators and the configured initial administrator retain the intended access.
- Discord sends suppress implicit mentions. Only actual/simulated raid messages may ping the configured raid role; recovery and connectivity notices never ping it. User names/text are escaped or sanitized.
- Source inspection found no hardcoded login tokens and no Discord-to-shell/eval path. SQLite inputs use bound parameters. Logs record controlled messages and sanitized codes rather than raw transport packets, URLs or tokens.
- `.env`, default pairing credentials, `*pairing*.json`, data directories and SQLite files are excluded from Git and the Docker context. Arbitrarily named custom pairing files must still be kept outside the project; ignore patterns cannot infer every secret filename.
- Docker runs as UID 1000, drops capabilities, disallows new privileges and persists a named SQLite volume. The default Compose file exposes no ports; optional website mode maps only 127.0.0.1:3080 for an existing HTTPS reverse proxy. No Steam password is stored. Keep reverse-proxy body/debug logging disabled for pairing requests.

Residual operational risk: Discord notification delivery is at-least-once, offline alarm edges cannot be reconstructed, and sufficiently long outages can outlive Rust's retained chat history. These limitations are documented rather than converted into fabricated events or automatic uncertain-write retries.

Website pairing extension: the server generates a Manifest V3 ZIP scoped to its configured website origin and the official Facepunch companion origin. It has no Steam host permission, cookies permission, remote code, external services or persistent token storage. A MAIN-world bridge captures the documented native handoff only in marked login tabs; an isolated relay sends it to the service worker. The worker validates the sender origin/frame/tab, expiration and original website document before delivering. Genuine loopback redirects are also observed and must match the exact stored callback. Payloads are validated again by the website and its existing cookie/CSRF/challenge/nonce checks. Registration still requires the user's Create Discord command action. Tokens are transient IPC/HTTP data, never URL navigations performed by the extension, browser storage or logs. Login metadata and the public Discord challenge may live in tab/session storage until expiry/browser close. The extension never hides or approves Facepunch's third-party warning. Compromise of either trusted origin or the user's browser remains outside this protection. No authenticated live consent or real Chrome extension integration was verified by unit mocks; complete the deployment checklist before sharing it.

Extension 1.0.1 uses a readiness exchange that works in either MAIN/ISOLATED script startup order. A successful handoff is acknowledged before the relay requests login-tab cleanup; metadata records delivery without storing tokens and rejects duplicate results. Failed handoffs can report only a fixed error to the original, bound website document. No credentials are included in failure messages or console warnings. Mocked regressions cover both load orders, acknowledgement timing, rejected/closed message ports, retry after failed delivery, and outdated-extension detection. Actual Chrome/Steam consent still requires a live smoke test.

Extension 1.0.2 fixes an incorrectly restrictive token alphabet confirmed by a user's token-free diagnostic: Facepunch returned a string token containing standard Base64 symbols. The companion token is treated as opaque bounded printable ASCII by one shared validator; whitespace, controls, non-ASCII and oversized inputs remain rejected. No token is decoded or normalized. URLSearchParams and JSON transport preserve `+`, `/` and `=` exactly. The extension, webpage and backend all use the same validator, and the website requires the updated extension. Failure codes and explanations are allowlisted static strings, never upstream exception messages, arbitrary event data or credentials. Synthetic tests cover exact token preservation through registration, malformed tokens and safe diagnostics; no live credentials were used in tests.
