# Rust+ Discord Base Bot

A self-hosted, multi-server / single-guild bot for your friends: native Discord base controls, real Smart Alarm notifications and two-way Rust team chat using each member's personal Rust+ identity. TypeScript, discord.js 14.27.0, rustplus.js 2.5.0 and SQLite. An optional pairing page runs on your own VPS behind your HTTPS reverse proxy. No external hosted database or dashboard is required.

## Existing installation: easier pairing and multiple servers

Your current `.env`, SQLite registrations, alerts, roles and panel IDs continue to work. The original server becomes profile `default`; the configured administrator's existing Rust+ pairing is imported as their personal chat identity once. **Other Discord members must now link their own Rust+ pairing to send chat. There is no shared-account fallback.** Rust-to-Discord chat remains available without linking every reader.

Back up the **entire** data volume before upgrading, then rebuild/recreate the image. The first run creates `/app/data/credentials.key` (local: beside `DATABASE_PATH`) and additional databases in `servers/` beside the original database. Newly imported server, FCM and personal player credentials are encrypted with this key. Keep the key with private backups: losing it makes saved credentials unreadable. Steam passwords, Steam Guard codes and cookies are never transferred to the bot. Browser pairing temporarily sends a Rust+ companion auth token to your VPS solely for push registration; it is not logged or persisted. Existing `.env` secrets remain in `.env`.

### Recommended: pair through your own HTTPS website

Friends use Discord, Chrome/Edge and Rust. `/pair start` opens your private website link. **Install the small website pairing extension once**, then sign in on **Facepunch/Steam's own page** from the website's button. The extension returns the login to the original website tab. Click **Create Discord command**, then paste the **encrypted** `/pair import` command into Discord. No desktop app, Node.js or terminal is required. After `/pair status` shows listening, pair in-game and open `/pair inbox`. Each incoming item has **Accept** / **Decline** buttons; Accept opens a naming dialog, including a destructive-equipment choice for switches. Decline removes only the pending entry, not an existing registration. Existing slash commands remain available.

**Why an extension?** The observed Facepunch flow lands on `/app?returnUrl=...` and redirects to the official app page instead of the requested localhost callback. The upstream [rustplus.js login implementation](https://github.com/liamcottle/rustplus.js/blob/master/cli/pair.html) handles a `ReactNativeWebView.postMessage` app bridge. An ordinary website cannot install that bridge in another origin. The extension installs it only in login tabs marked by this website's login flow, without changing the consent UI or disabling browser security. Steam OpenID alone cannot authorize Rust+ chat. A genuine legacy localhost callback can still be pasted under **Manual callback or redirect troubleshooting**, but the primary flow no longer depends on that redirect.

The ZIP is generated by your own bot at `/pairing-extension.zip` for exactly your configured `PAIRING_WEB_URL`. It requests access only to that origin and `companion-rust.facepunch.com`, plus session storage and HTTP redirect observation. It does not access Steam pages, passwords or cookies, does not log/store auth tokens, and sends the Rust+ result only to the original website tab/document. Temporary metadata expires after 15 minutes and disappears on browser close. Registration continues on the VPS using the installed rustplus.js 2.5.0 CLI's FCM/Expo/companion protocol. This is unofficial; mocked tests do not verify real Steam consent, Chrome's actual injection timing or live FCM registration.

One-time browser setup: download the ZIP from the pairing page and extract it to a permanent folder. Open `chrome://extensions` (Edge: `edge://extensions`), enable **Developer mode**, choose **Load unpacked**, then select the folder containing `manifest.json`. **Refresh the pairing website**; your temporary public Discord code is retained in tab session storage for this refresh. Continue and check **Extension connected** before signing in. The extension is self-hosted and **not published in a browser store**; Chrome cannot silently install an ordinary ZIP. Keep the folder while installed. Download/replace files and click **Reload** on the extension card for updates, then refresh the website. A hostname change requires a new ZIP. Chrome/Edge 111+ desktop is supported; mobile browsers and Firefox/Safari are not packaged here. You may disable/remove the extension after Discord import; VPS monitoring and future in-game pair notifications continue.

**Still redirected to `https://rust.facepunch.com/companion`?** No pairing has completed. Verify this domain's extension is enabled, refresh the website, obtain a fresh `/pair start` link if expired, and launch Steam from the website button. Independently opened old login tabs are not associated with the current session. Complete the official Facepunch warning yourself. If blocked, report only the route/domain and visible error, never the token or page source. No DNS/Nginx changes or browser-security flags are needed for the handoff. The desktop helper below remains a legacy option when website mode is disabled; website mode does not advertise it.

**Continue does nothing on Facepunch's `/app` page?** Update both the VPS and extension to **1.0.2** or later: download a fresh ZIP from the updated pairing website, replace the files in your existing extracted folder, and click **Reload** on its `chrome://extensions` card. Close old Facepunch login tabs, refresh the pairing website, and start a fresh sign-in from its button. Updating the VPS alone does not update an unpacked browser extension. Version 1.0.1 fixed readiness and acknowledgement timing, but incorrectly rejected standard Base64 characters in Facepunch's token. Version 1.0.2 shares opaque-token validation across the bridge, worker, website and backend; it preserves `+`, `/` and `=` unchanged through URL/JSON encoding. Failed handoffs report fixed diagnostic codes such as `AUTH_TOKEN_FORMAT`, `MESSAGE_PORT` or `WEBSITE_RECEIVER`, without exposing credentials. Keep the original website tab open without refreshing during sign-in; report only the error code if a failure remains.

Owner setup, once (existing domain + HTTPS required):

1. Back up your data volume. Put the updated code on the VPS and keep your existing working Docker security/execution settings.
2. Set `PAIRING_WEB_URL=https://pair.example.com` in the VPS `.env`, replacing the example with **your HTTPS hostname**. Use an origin only, without a path, query or fragment. A dedicated subdomain is recommended. Leave the variable blank to disable the website and keep the desktop flow. `PAIRING_HELPER_URL` applies only to that desktop-only mode.
3. Build/start using the optional Compose override. It binds port 3080 to **host loopback only**, for a reverse proxy running on the VPS:

   ```sh
   sudo docker compose -f docker-compose.yml -f docker-compose.web.yml config --quiet
   sudo docker compose -f docker-compose.yml -f docker-compose.web.yml up -d --build --force-recreate rust-bot
   sudo docker compose -f docker-compose.yml -f docker-compose.web.yml logs -f --tail=50 rust-bot
   ```

   Use both `-f` files for later updates/recreation too. The named data volume is unchanged. Do not open port 3080 publicly. The bot logs that its pairing website is listening; it remains usable for controls/chat when no pairing is underway.

4. Forward the **root of that HTTPS hostname** to `http://127.0.0.1:3080`. Preserve the browser's `Host` and `Origin`. For an existing Nginx TLS server block:

   ```nginx
   # Inside your existing server { listen 443 ssl; server_name pair.example.com; ... }
   location / {
       proxy_pass http://127.0.0.1:3080;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-Proto $scheme;
       proxy_read_timeout 90s;
       client_max_body_size 16k;
   }
   ```

   Validate/reload using your normal Nginx procedure (`sudo nginx -t`, then `sudo systemctl reload nginx`). For Caddy, an equivalent hostname block is `pair.example.com { reverse_proxy 127.0.0.1:3080 }`. If the proxy itself is a container, attach it to the bot's Docker network and use `rust-bot:3080` instead of the proxy container's own loopback. Preserve your existing certificates and redirect HTTP to HTTPS.

5. Open your HTTPS URL to check the page, then run `/pair start` in Discord and use **Open pairing website**. Test with your own account before inviting friends. A bot restart, a new `/pair start`, import, or unlink invalidates an old code. Codes expire after 15 minutes.

Do not enable reverse-proxy request-body capture/debug tracing or browser analytics for this page. The app logs no pasted addresses/tokens and sends `no-store`, `no-referrer`, strict CSP and secure HttpOnly session cookies. Registration runs in bounded workers (maximum two, 60-second deadline); failures do not block Rust connections. Temporary sessions/results live only in memory. Failed upstream registration is reported without raw error bodies. Existing dependency advisories still apply to the registration stack; see [SECURITY_REVIEW.md](SECURITY_REVIEW.md).

Discord panels now share consistent server context and styling. `/server list` has a default-server dropdown and administrator pause/resume buttons. `/device list` and `/alarm list` have pagination, selection, state refresh, rename dialogs and confirmed registration removal; alarms also have notification/test buttons. `/chat status` has administrator enable/disable buttons. `/status` has a refresh button. Controls always fetch current permissions. Device removal is bot-side deregistration; physical Rust pairing/access is managed in-game. `/pair status` includes a confirmed personal-account unlink button.

### Desktop helper fallback

1. Run `/pair start` in Discord. It returns a private pairing code valid for 15 minutes and a **Download Windows pairing helper** button when the owner has configured its download URL.
2. Download the helper ZIP, choose **Extract all**, open the extracted folder and double-click **RustPlus Pairing.cmd**. Your friends do **not** need this repository, Node.js, npm, a terminal, a Discord bot token or administrator access. Windows 10/11 x64 and Google Chrome are required; Node.js and dependencies are included in the ZIP.
3. Paste the Discord code into the helper and click **Link account**. If needed, Chrome opens the upstream Rust Companion/Steam login flow. Log in on Steam's page. Click **Copy Discord command**, paste into Discord and send. Only encrypted credential data travels through Discord. Raw tokens are not displayed by the helper.
4. Close any local `fcm-listen` using that registration. The **VPS** now keeps the FCM listener running, including after restarts. Check `/pair status` for `listening` before pairing in-game. Allow outbound TCP **5228** to `mtalk.google.com` and outbound HTTPS as appropriate; no inbound VPS ports are required.
5. In Rust, click **Pair with Server**. Run `/pair inbox`, then `/pair accept id:<pairing-id>`. Administrators can add monitored servers; operators can link only to existing servers. Chat checks that your Steam account belongs to the mirrored Rust team before dispatch.
6. For a Smart Switch/Alarm, use **Pair** on the device in-game, then `/pair inbox` and Accept, or `/pair accept id:<pairing-id> name:Garage`. Devices require administrator approval. Choose **yes** for destructive equipment in the dialog, or set `sensitive:true` in the command. Pairing only registers/queries the device; it never activates it. Reaccepting an existing registration can update its name and add a safety flag, but never clears an existing safety flag.

This removes the recurring need to run `fcm-listen` or copy raw IDs/tokens. Browser sign-in and the in-game Pair action remain necessary. Close the helper after import. If FCM reports `invalid-credentials` or you want another Steam account, get a new `/pair start` code and check **Sign in again** in the helper. Inbox pairings are private, deduplicated and expire after 24 hours. The helper stores only the local FCM listener registration in `%LOCALAPPDATA%\RustPlusDiscordPairing\rustplus.config.json` after a successful run; **Reset local registration** removes that file. Use `/pair unlink` to remove credentials on the bot as well.


Desktop-only mode has no inbound HTTP listener.

The desktop helper reuses the installed rustplus.js registration CLI. Its packaged copy binds the temporary port-3000 login callback to loopback and uses chrome-launcher's isolated temporary browser profile rather than upstream's hardcoded Unix profile path. The upstream login flow relaxes browser security for that dedicated Chrome session; use it only for pairing and close it when finished. Raw upstream stdout/stderr are suppressed. Failed or cancelled sign-in gets a visible error/timeout, and closing the helper stops its registration process tree. Developer/Linux/macOS fallback is still available from this repository: `npm ci`, then `npm run pair -- --code <code-from-discord>`. ### Multiple servers without restarting the bot

Enabled profiles run simultaneously, each with independent devices, subscriptions, panels, alarm cooldowns/outboxes, chat history and channel settings. Additional servers do not inherit the first alert destination. After accepting a server pairing:

```text
/server list
/server use
/settings alerts channel:#second-alerts
/chat setup channel:#second-chat
/panel
```

With multiple saved servers, server-specific slash commands open a **private server dropdown** when you omit `server`. Choose by name; the command then runs with the channel, device ID, role and other options you already entered. Nothing runs before selection. This includes `/panel`, `/device`, `/alarm`, `/chat`, `/settings`, `/status`, `/ping`, `/pair status`, and `/server use|pause|resume`. `/server use` no longer requires an ID. With one saved server, commands run directly. Explicit `server:<id>` and `/server use id:<id>` still skip the picker. Global help, server listing and pairing sign-in/inbox/unlink continue to open directly; accepted pairings identify their server from the notification.

Selections belong to their initiating member, expire after five minutes and can be cancelled. The bot checks current permissions before showing choices and again before execution; duplicate submissions cannot execute a command twice. Up to five prompts per member and 200 total are retained in memory; pending selections expire on bot restart, so rerun the command. Choosing a server for a command does not change your saved `/server use` default.

Configure operator roles per server with `/settings role-add role:@Operators`, then choose the server. Panel buttons always target the server belonging to their saved message, and ordinary chat messages still route through the configured channel. Use distinct panel channels. **Alert channels may be shared:** run `/settings alerts channel:#alerts` and select each server in turn; notification footers identify the server.

Each chat channel belongs to one server at a time. Administrator `/chat setup channel:#rust-chat` **transfers** an occupied channel to the server you select, disables the previous bridge and clears its channel assignment. Pending old-bridge sends are invalidated; a request already sent to Rust cannot be recalled. The picker appears even when you invoke the command in another server's chat channel. Run `/chat setup` again to give the previous server a different channel before enabling it.

`/server pause` and `/server resume` affect only the server you select; paused servers remain available in the picker. Fresh pairing by an administrator for the existing monitoring Steam identity refreshes its token without replacing devices. A friend's pairing links personal chat and does not replace the monitoring account. Use these commands to switch servers instead of changing the original environment variables. Up to 10 server profiles and 50 paired users are supported.

Every chat author needs their **own Rust+ server pairing**, not just Steam OpenID or a Steam ID. Messages use their player ID/token and retain the `[Discord] DisplayName:` prefix. Personal connections open on demand, reuse existing sockets, and close after 60 seconds idle. At most three additional personal connections per server run alongside monitoring, below the upstream documented default of five per source IP/server, assuming no other automation or alternate-hostname profiles share that endpoint. Stricter server limits may require fewer active users. Uncertain sends are not retried automatically; rejected personal credentials pause until a new pairing. `/pair unlink` removes your listener and personal chat credentials across servers; shared monitoring remains configured. An explicitly unlinked administrator is not automatically relinked on restart.

### Player online/offline and death notices

The configured alert channel also receives **Player Online**, **Player Offline** and **Rust+ Death Notification** embeds, with the server name in the footer. These notices do not ping the raid role. No new environment variables or browser-extension update are needed.

Online/offline monitoring covers players visible in the monitoring account's Rust team, independently of whether chat is enabled. It combines live `teamChanged` broadcasts with a 30-second `getTeamInfo` poll using the protocol's `isOnline` field. The first snapshot after startup/reconnect is a silent baseline; joining/leaving the team does not fabricate login/logout events. Activity during a monitoring gap is not reconstructed.

Offline death notifications are forwarded from actual Rust+ **player/death FCM pushes**, not inferred from a body or an alarm. The affected player must link their own account through `/pair start` and accept that server pairing; `/pair status` must show a listening push registration. The bot routes the push to that accepted server's alert channel even when its Rust WebSocket is disconnected. Push delivery may be delayed or unavailable upstream, so these are reports rather than exact death timestamps or confirmed raids. Unlinked players' deaths are unavailable. Paused servers do not forward them.

Push IDs are deduplicated persistently across restarts, with a 30-second fingerprint fallback for multiple registrations of the same Steam account. Identical reports within that window coalesce. Discord failures use the existing persistent notification outbox and retries; delivery is at-least-once. Wire-format references: [Rust+ team protocol](https://github.com/liamcottle/rustplus.js/blob/master/rustplus.proto), [Rust+ push documentation](https://github.com/liamcottle/rustplus.js/blob/master/docs/API.md) and [Rust++ FCM event handling](https://github.com/alexemanuelol/rustplusplus/blob/master/src/util/FcmListener.js).

## Before you start

You need a Discord server where you can invite a bot, a Steam account that can join the Rust server, and a Rust server with Rust+ enabled and reachable. **You do not need server administrator access.** The server operator must already have enabled its companion port; a player cannot enable Rust+ on a server where it is disabled.

Use Node.js 22.13 or newer (Node 22 LTS recommended), or Docker Engine with the Compose plugin on an x86-64 Ubuntu VPS. SQLite uses Node's bundled `node:sqlite`, so no native database compilation is required. Some Node 22 releases print an experimental SQLite warning.

## 1. Create and invite the Discord bot

1. Open the [Discord Developer Portal](https://discord.com/developers/applications), create an application, and create/reset its bot token under **Bot**. Keep the token private.
2. Enable **Message Content Intent** under Bot → Privileged Gateway Intents. The bot requests Guilds, Guild Messages and Message Content. It fetches individual members for role checks; Server Members and Presence privileged intents are not required.
3. Copy the application's **Application ID** to `DISCORD_CLIENT_ID`. Enable Discord **User Settings → Advanced → Developer Mode**; right-click your server and your user to copy `DISCORD_GUILD_ID` and `ADMIN_USER_ID`.
4. Under **OAuth2 → URL Generator**, select `bot` and `applications.commands`. Grant **View Channels**, **Send Messages**, **Embed Links**, and **Read Message History**. Open the generated invite URL and add the bot to your guild. Do not grant Administrator to the bot.
5. Ensure channel permission overrides allow these permissions in the panel, alarm and chat channels. For alert pings, make the chosen alert role mentionable. Alternatively grant **Mention @everyone, @here, and All Roles** only in the alarm channel. The bot explicitly allows mentions of the configured role only.

Commands are registered for the configured guild at startup. All administrative commands enforce authorization in the application; the configured initial administrator can use them even without Discord's Administrator permission. Other server administrators also have administrative access. Operator roles can use switch buttons and relay chat, but cannot modify settings.

## 2. Obtain Rust+ server credentials (public servers supported)

Perform pairing on your desktop with Chrome installed, rather than trying to open a browser on the VPS. See the upstream [pairing instructions](https://github.com/liamcottle/rustplus.js#pairing) and [pairing flow](https://github.com/liamcottle/rustplus.js/blob/master/docs/PairingFlow.md).

```sh
npx @liamcottle/rustplus.js fcm-register
npx @liamcottle/rustplus.js fcm-listen
```

`fcm-register` launches a special Chrome profile and opens the Rust Companion/Steam sign-in flow. Sign in in that browser. This bot never asks for or stores a Steam password or Steam Guard code. The upstream CLI stores push/auth registration material in `rustplus.config.json`; treat that file as a secret. Its temporary browser disables web security for the pairing flow: use it only for pairing and close it afterwards.

While `fcm-listen` runs:

1. Join your existing public Rust server with the same Steam account.
2. Open the in-game Rust+ menu and click **Pair with Server**.
3. Read the server pairing notification in your terminal. Copy **ip**, **port**, **playerId**, **playerToken** into the corresponding environment variables:

| Notification field | Environment variable |
| ------------------ | -------------------- |
| `ip`               | `RUST_SERVER_IP`     |
| `port`             | `RUST_APP_PORT`      |
| `playerId`         | `RUST_STEAM_ID`      |
| `playerToken`      | `RUST_PLAYER_TOKEN`  |

Use the notification's **app port**, not the game or RCON port. The Steam64 ID is a 17-digit string; the player token is a signed 32-bit integer and can be negative. Keep both tokens out of screenshots and logs shared with others. Re-pair if the server revokes your token or changes pairing data. Change `.env` and recreate the container to load updated credentials.

The CLI can use an explicit file if needed:

```sh
npx @liamcottle/rustplus.js --config-file=./private-pairing.json fcm-register
npx @liamcottle/rustplus.js --config-file=./private-pairing.json fcm-listen
```

Keep any custom pairing file outside the project. This manual flow bootstraps the first server or recovers without Discord. The bot needs neither Chrome nor the full desktop registration file: `/pair import` transfers only encrypted FCM Android ID/security-token material so the VPS can listen for later pairings. Pairing depends on third-party FCM/Expo/Steam services and may need upstream fixes if those services change.

## 3. Obtain Smart Switch and Smart Alarm entity IDs

Prefer `/pair start` and the VPS listener above, then pair in-game and accept through `/pair inbox`. For manual registration, keep `fcm-listen` running, look at your **Smart Switch** or **Smart Alarm**, and use its in-game **Pair** interaction. Use the notification's entity ID for `/device add`. Normal in-game device access is required; administrator-only debug commands are unnecessary. Do not run the VPS listener and local `fcm-listen` against the same registration concurrently.

Do not substitute an electrical branch/ordinary switch/door ID. A door cannot be controlled directly: wire a **Smart Switch** to the desired circuit. Register devices paired to the same Steam account and server as the bot. After a wipe, destroyed/replaced devices usually need fresh pairing and registration. The bot verifies registered device types when it queries Rust+; an inaccessible or mismatched device is shown as unknown and retried.

## 4. Configure and run locally

Copy `.env.example` to `.env` and fill the required fields. On Linux:

```sh
cp .env.example .env
chmod 600 .env
npm ci
npm run check
npm start
```

On PowerShell use `Copy-Item .env.example .env`. For development use `npm run dev`. The first startup creates the database and registers guild slash commands. Missing/invalid environment fields produce a startup error identifying the fields without printing their values.

`RUST_USE_PROXY=true` connects through Facepunch's secure WebSocket proxy. Use `false` only when you need a direct connection: direct `ws://` is unencrypted. Neither mode requires opening an inbound port on the VPS. Allow outbound HTTPS/WSS and, for direct mode, TCP to the server's app port. Run only one bot instance per SQLite database and avoid competing Rust+ automation under the same player identity.

Optional settings:

| Variable                                | Default / meaning                                                                       |
| --------------------------------------- | --------------------------------------------------------------------------------------- |
| `DATABASE_PATH`                         | `./data/bot.sqlite`; overridden to `/app/data/bot.sqlite` in Compose                    |
| `ALLOWED_ROLE_IDS`                      | Empty: administrators only. Comma-separated initial operator roles                      |
| `ALERT_CHANNEL_ID` / `ALERT_ROLE_ID`    | Optional initial alert channel and role                                                 |
| `BASE_NAME`                             | Main Base                                                                               |
| `ALARM_COOLDOWN_SECONDS`                | 60; per alarm, persisted across restarts                                                |
| `CHAT_POLL_SECONDS`                     | 30; minimum 10                                                                          |
| `RUST_CHAT_MAX_LENGTH`                  | 128 UTF-16 units; adjustable down to 64 for stricter servers                            |
| `LOG_LEVEL`                             | info; structured JSON to stdout                                                         |
| `PAIRING_WEB_URL`                       | Empty: website disabled. HTTPS origin for your self-hosted pairing page                 |
| `PAIRING_WEB_HOST` / `PAIRING_WEB_PORT` | `127.0.0.1` / `3080`; web Compose override binds container 0.0.0.0 behind host loopback |
| `PAIRING_HELPER_URL`                    | Optional HTTPS download of the desktop helper ZIP; website fallback                     |

Settings changed through Discord are saved in SQLite and override the corresponding **initial** environment role/alert defaults. Each server database is bound to its Rust server and monitoring player identity to prevent accidental control of unrelated entities. Add other servers through pairing/server profiles; the bot manages their separate databases in the same data volume.

## 5. First-time Discord setup

Run these as `ADMIN_USER_ID` or a Discord guild administrator. Entity IDs below are examples: replace them with your actual pairing IDs.

1. `/settings role-add role:@RustFriends` allows friends to operate switches and send team chat. With no allowed roles, only administrators can operate them.
2. `/device add id:123456 name:Garage Door Power type:Smart Switch` registers your first switch. Use `sensitive:true` for any potentially destructive circuit, regardless of its friendly name.
3. `/panel` creates the control panel in the current channel. Run it again to refresh the saved message. Four switches fit on each page, with navigation buttons for additional devices. The saved message and button handlers survive restarts.
4. `/settings alerts channel:#raid-alerts role:@RaidTeam` configures notifications. Omit the role to clear the role ping.
5. `/device add id:654321 name:Outer Wall type:Smart Alarm` registers an alarm. Wire it to your in-game sensors and provide power. Rust+ itself does not detect raids.
6. `/alarm test id:654321` sends an explicitly **simulated** Discord alert. It never changes an in-game device. Then test a real inactive → active sensor transition in-game.
7. Join/create a Rust team using the paired Steam player. `/chat setup channel:#rust-team` configures and enables the dedicated chat channel. Wait for `/chat status` to show **Live**, then test messages in both directions.
8. Check `/status` for connection state, server/player information, registered device count and chat health.

The panel reports actual **Smart Switch ON/OFF**, never inferred door position. Buttons acknowledge privately, show work in progress, disable while busy/disconnected, and read the device after a command. Persistent IDs never bypass role or device-registration checks. Sensitive switches require a short-lived, user-bound confirmation for state changes; names containing terms such as explosives, detonator, rocket or C4 also activate that safeguard. Explicitly mark other hazardous circuits sensitive when registering them.

Administrative responses are ephemeral. The panel and alerts are channel messages. Discord-to-Rust relay only accepts ordinary non-bot, non-webhook messages from authorized members in the configured channel. Attachment-only messages are ignored; when a message has text and attachments, only its text is relayed. Embeds, stickers and attachment URLs are not fabricated into plain text.

## Chat and recovery behavior

Rust's protocol exposes `broadcast.teamMessage.message`, `getTeamChat` history and `teamChanged`. The bot combines live messages with periodic history polling and team-information checks. It uses Steam identity + protocol timestamp + text as a persistent deduplication key (the protocol has no unique team-message ID), plus short-lived fingerprints. Discord message IDs suppress duplicate outgoing events. Echo text from the connected Steam identity is recorded before sending, including in SQLite, so the connected player's Discord-origin messages do not loop back.

Player names and text are preserved in bot embeds with a `[Rust]` author label. This uses the ordinary bot-message fallback rather than player webhooks, avoiding webhook-token storage and extra permissions. Mentions cannot ping Discord roles/users through relayed messages. Outgoing messages use `[Discord] DisplayName: text`; mentions/markdown/control characters are sanitized, long messages are split with a prefix on each part, and more than eight parts are rejected. Both directions use ordered queues with bounded capacity. Different message sources and simultaneous game events can still arrive out of timestamp order.

At startup, reconnect, team change, or re-enabling chat, the first history snapshot is **baseline-only**: old messages and messages sent while the bridge was offline are intentionally not replayed. Live chat resumes after synchronization. Polling recovers messages missed within an active session while the server retains them. A disconnected bridge tells an authorized Discord sender that their message was not relayed. Uncertain Rust sends are not automatically retried, since that could duplicate a delivered message.

Smart Alarm baselines never trigger ordinary raid alerts. Only a live inactive → active broadcast triggers a raid alert. If an enabled alarm is already active when its monitoring baseline is established at startup/reconnect, a separate **⚠️ Alarm Active After Reconnection** warning explains that the activation time and cause are unknown. This warning never claims a raid or pings the raid role. It is suppressed across reconnects and process restarts until an inactive state is observed. Disabled/deleted alarms do not produce recovery warnings; disabling removes pending alerts and warnings. Cooldowns still apply to normal raid alerts and survive restarts.

Observed activations and cooldown timestamps are committed together in SQLite before Discord delivery; failed sends retry with capped backoff and survive restarts. Multiple undelivered activations of the same alarm coalesce into one pending alert showing its original observation time. Discord delivery is at-least-once: a crash after Discord accepts a notification but before its local acknowledgement can cause a duplicate. No bot can observe alarms while Rust+ or its host is unreachable; events during an offline Rust session are not reconstructed from an active snapshot.

After the first initialized connection, a continuous Rust+ outage of **60 seconds** queues one **⚠️ Rust+ Connection Lost** notification in the existing alert channel. Reconnection attempts do not repeat it. A single recovery notification follows authentication and device initialization, includes approximate downtime, and explicitly says **Degraded Monitoring** if required devices failed to subscribe. Failed subscriptions retry on the 30-second maintenance cycle; `/status` reports the current device health and last successful connection time. A fresh startup or a brief outage does not produce connection notices. A previously recorded outage resumes across a process restart. These operational notices do not ping the raid role. If Discord is unavailable, SQLite retains the notices in outage order and retries after Discord reconnects. Configure `/settings alerts` to receive them.

The Rust connection authenticates by requesting server info, restores each device subscription with `getEntityInfo`, and periodically probes the server to catch half-open connections. Failed transport/timeout requests reconnect with capped exponential backoff and jitter. Invalid-token/authentication responses stop retries and show `invalid-credentials` until you re-pair and restart. Requests are serialized, bounded and paced below the documented player budget: one token every 800 ms, two tokens for chat. A rate-limit response pauses subsequent work for ten seconds. Mutating requests are never blindly retried. discord.js handles Discord gateway reconnects and REST rate limits.

## 6. Ubuntu VPS deployment with Docker Compose

Install [Docker Engine and its Compose plugin](https://docs.docker.com/engine/install/ubuntu/) from Docker's Ubuntu instructions. Upload/clone this project to your VPS, excluding your local `.env`, data and pairing files. Create `.env` privately on the VPS with the paired server fields and Discord credentials.

```sh
# First build and start (no inbound ports are published)
docker compose build --pull
docker compose up -d

# Status and logs
docker compose ps
docker compose logs -f --tail=100

# Graceful stop; preserve the named database volume
docker compose stop

# Start again
docker compose start

# Update code, then rebuild/recreate
git pull
docker compose up -d --build

# Reload changed .env values
docker compose up -d --force-recreate

# Remove containers/network while retaining the database volume
docker compose down
```

If you uploaded an archive instead of using Git, replace files with the newer release before the rebuild. The image uses a production dependency tree, runs as the unprivileged Node user, drops Linux capabilities and persists `/app/data` in `bot-data`. It has no exposed ports. `restart: unless-stopped` restarts after process failures or host reboots; an explicit stop remains stopped. A `.env` validation failure requires fixing configuration, not repeated restarts. Do **not** use `docker compose down -v` unless you intend to permanently erase the saved configuration.

Back up the entire data directory while stopped, including any SQLite WAL/SHM files. From this project directory:

```sh
docker compose stop
docker compose run --rm --no-deps --entrypoint tar rust-bot -C /app/data -czf - . > rust-bot-data.tar.gz
docker compose start
```

To restore, stop the service and extract the entire backup into its named volume with ownership readable/writable by UID 1000 (the container's Node user). Keep backups private: the databases now include encrypted Rust+/FCM credentials, and `credentials.key` is required to decrypt them. Include every `servers/*.sqlite` database, WAL/SHM files and the key. Discord tokens and Steam passwords are not stored in SQLite. Use server profiles to switch servers; after a wipe, deliberately remove/re-pair obsolete devices.

## Troubleshooting and validation

- **`exec ...: operation not permitted` before application logs:** this is a container execution failure, not a Discord/Rust credential error. If disabling `init` just changes the blocked path from `docker-init` to `docker-entrypoint.sh`, the restriction is broader than the init helper. Compare disposable runs of the built image with `--entrypoint /usr/local/bin/node --cap-drop ALL` and then the same command plus `--security-opt no-new-privileges:true`, passing `--version` as the Node argument. These probes need no environment file or data volume. If only the second fails, the host's security policy conflicts with no-new-privileges; inspect `docker info` and kernel AppArmor denials before changing the host. A host-specific workaround is removing just the two-line `security_opt` block, which removes the extra privilege-escalation guard; retain the non-root user, capability dropping and Docker's other default isolation. Do not disable AppArmor/seccomp globally or use privileged mode. Fixing the host's Docker/security integration is preferable; back up volumes before changing Docker installations. This bot can run without `init` because it handles SIGTERM/SIGINT and does not spawn child processes.
- **Commands missing:** confirm application ID, guild ID, invite scopes, and startup logs. Guild command registration requires the bot to be installed in that guild.
- **Discord 401 / startup failure:** reset/update the bot token. For unavailable intents, enable Message Content Intent and restart.
- **No Rust+ connection:** use the pairing notification's game-server IP/app port (not the VPS IP or game/query port), verify the server supports Rust+, and check outbound firewall rules. Transport error logs identify the `proxy`/`direct` route, a safe `reason`, and `httpStatus` when the WebSocket upgrade is rejected; raw error messages and credentials are omitted. Errors while still `connecting` occur before player-token authentication. A proxy HTTP failure alone does not distinguish an unavailable proxy from an unreachable game-server app port; compare connectivity through both routes before changing credentials. Direct `ws://` transport is unencrypted. A game-server restart may briefly interrupt service.
- **Invalid credentials:** re-pair the server with the matching Steam account, update the token and recreate the container. Never paste tokens into Discord.
- **`ProtocolError` during synchronization or chat setup:** rustplus.js 2.5.0 requires metadata fields that Rust servers can omit when they have default values. Examples include `AppInfo.queuedPlayers`, offline team members' `isOnline`/`isAlive`, zero coordinates/timestamps, and map-note `type`. The bot applies an in-memory compatibility fix to server/team metadata before its first request on every connection, preserving protobuf defaults (`false`, `0`, empty strings), identity and message-text requirements, response sequence requirements, and device type/payload validation. It does not edit `node_modules` or change entity type IDs. Update the source and rebuild the image if using an older bot build. Unexpected decoding failures cancel pending requests and enter normal reconnection, with safe schema-field diagnostics when available, rather than crashing the process. If an older build reconnects repeatedly after enabling chat, temporarily run `/chat disable` while updating. See upstream [issue #81](https://github.com/liamcottle/rustplus.js/issues/81), [PR #77](https://github.com/liamcottle/rustplus.js/pull/77) and [PR #82](https://github.com/liamcottle/rustplus.js/pull/82).
- **Unknown devices:** check entity ID, type, Steam pairing identity and server. Re-pair and re-register after a wipe or entity replacement. Maximum 100 registered devices.
- **No raid alert / alarm test fails:** first run `/settings alerts channel:#raid-alerts` without a role and allow the bot **View Channel**, **Send Messages** and **Embed Links** in that channel, including category/channel overrides. Retry `/alarm test id:<registered-alarm-id>`; this tests Discord delivery without contacting Rust+. A saved channel setting in SQLite overrides `ALERT_CHANNEL_ID`, so changing the environment alone may not select a new destination. Once the test succeeds, optionally configure a mentionable raid role, enable alarm notifications, confirm electrical power/wiring and test a real inactive → active sensor transition. Check cooldowns. Expected missing-channel/access/permission errors have actionable ephemeral responses; unknown errors remain private and their code is logged.
- **Chat unavailable:** the paired player must belong to a Rust team; verify the channel, operator role and Message Content Intent. Check `/chat status`. No messages are forwarded while chat is synchronizing.
- **Panel missing/deleted:** run `/panel` to recreate a deleted saved message. Check Read Message History and Embed Links permissions.

```sh
npm run typecheck
npm run lint
npm test
npm run build
docker compose config --no-env-resolution --quiet
docker build -t rust-discord-base-bot .
```

Tests use mocks, controlled timers, local SQLite and a loopback WebSocket server with the installed rustplus.js library and protobuf schema. They cover permission isolation, actual button handlers, simultaneous controls, uncertain switch failures, chat ordering/polling/echo suppression, notification thresholds, recovery warnings, alarm edges/cooldowns, additive database migrations and subscription restoration. Successful automated checks do not establish that your real credentials, Discord permissions, public server configuration or in-game wiring work. Complete [DEPLOYMENT_CHECKLIST.md](DEPLOYMENT_CHECKLIST.md) before relying on the bot for alerts. See [REVIEW_REPORT.md](REVIEW_REPORT.md) for the pre-deployment review and [SECURITY_REVIEW.md](SECURITY_REVIEW.md) for each remaining dependency advisory.

## Implementation references

The integration was checked against the installed rustplus.js source and protocol, its [device broadcast example](https://github.com/liamcottle/rustplus.js/blob/master/examples/4_entity_changed_broadcasts.js), [request example](https://github.com/liamcottle/rustplus.js/blob/master/examples/6_async_requests.js) and [documented request budgets](https://github.com/liamcottle/rustplus.js#rate-limits). `src/rust/protocol.ts` defines only the protocol fields used by this bot. `src/rust/connection.ts` wraps the verified callback API with timeout cleanup; it deliberately consumes handled responses instead of emitting them again as generic messages.

Dependency overrides update protobufjs and the pairing CLI's form-data/qs packages. `npm audit` reports 11 moderate advisories in upstream bundled dependencies, with no high or critical findings. The VPS now loads the push receiver for pairing, but its check-in uses native bounded fetch instead of the legacy request/retry helper; the affected request/cookie operations are not used on that runtime path. The desktop registration CLI still uses the legacy chain. Camera/file-type decoding and vulnerable uuid algorithms remain unused. No incompatible major overrides were introduced; review [SECURITY_REVIEW.md](SECURITY_REVIEW.md) and rerun protocol tests when updating. The lockfile remains reproducible.

Code is split into configuration/logging, SQLite storage, permissions, device/alarm transitions, the Rust connection manager, the team-chat bridge and Discord command/panel/alert modules. There is no arbitrary command execution path in Discord. Only registered switch entity IDs can reach a state-changing Rust+ request.
